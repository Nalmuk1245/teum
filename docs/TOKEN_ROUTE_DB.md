# 토큰 경로 DB — 설계 보고서

> 작성 2026-07-26 · 상태: **설계안(미구현)** · 배경: "매 순간 외부 API 호출은 느리다.
> 미리 토큰별 경로 DB를 만들어두는 구조가 낫지 않나"

---

## 1. 왜 필요한가 (측정된 현실)

`tokenResolve`는 **메모리 전용** 10분 캐시이고(`loadSection`/`saveSection` 사용 0회),
`quoteDex`에는 캐시가 없다. 즉 재시작할 때마다 전부 다시 부르고 있다.

| 항목 | 지금 |
|---|---|
| 콜드 상세 조회 | 0.44 ~ 1.72초 (체인 수에 비례) |
| 재조회(SWR 8초 적용 후) | 0.006초 |
| DexScreener 풀 조회 | ~95ms |
| CoinGecko 조회 | ~130ms |
| OKX 견적 | 300~600ms · **실패할 때 가장 느림** |

콜드 비용의 대부분은 **체인마다 도는 OKX 견적**이고, 그 앞단(어떤 체인에 무슨
컨트랙트가 있고 어디에 풀이 있나)은 **거의 변하지 않는 정보인데 매번 다시 캐온다.**

---

## 2. 저장할 것과 절대 저장하지 않을 것

이 선을 잘못 그으면 **낡은 값으로 주문을 넣게 된다.** 기준은 "규모와 그 순간의 호가
깊이에 의존하는가"다.

### 저장한다 — 정체성·지형 (며칠~몇 달 단위로 변함)

| 데이터 | 출처 | 재검증 주기 |
|---|---|---|
| 체인별 컨트랙트 주소 · decimals | CoinGecko | 30일 |
| 온체인 `symbol()` 검증 결과 | 체인 RPC | 30일 |
| 체인별 최상위 페어(풀) 주소 | DexScreener | 30일 |
| 이 코인을 상장한 CEX 집합 | 거래소 티커 | 6시간 |
| 거래소별 출금 네트워크 코드 | 거래소 API | 7일 |

### 캐시하되 실행 판단에 단독으로 쓰지 않는다

| 데이터 | 주기 | 용도 |
|---|---|---|
| 풀 유동성(USD) | 1시간, 배경 갱신 | "이 체인이 살아 있나" 1차 필터 · 표시 |

### 절대 저장하지 않는다 — 라이브 전용

**실행가 · 슬리피지 · 라우트 존재 여부 · CEX 가격 · 김프.**
규모와 그 순간 깊이에 달려 있다. 캐시된 값으로 판단하면 **없는 유동성에 주문을 넣는다.**

> 원칙: **DB는 "어디를 볼지"를 알려주고, 라이브 호출이 "지금 얼마인지"를 답한다.**
> 실행 경로는 DB를 신뢰 근거로 쓰지 않는다 — 언제나 재견적한다.

## 3. 어떤 DB를 쓸 것인가 → **기존 `persist.ts` 섹션 파일** (SQLite 아님)

### 요구사항

- 접근: `base` 심볼로 점 조회 (`EUL` → 경로). 전체 스캔은 거의 없음
- 쓰기: 상장 감지·최초 조회 시 토큰 1건 갱신 (드묾 — KR 신규 상장 주 1~3건)
- 동시성: 단일 프로세스·단일 사용자
- 내구성: **캐시다.** 잃어도 다시 만들면 된다 (돈이 아님)

### 규모 계산

토큰 1건 ≈ 270 bytes(3체인 기준). 실측: **300 토큰 = 80KB, stringify 1.75ms.**
1년 누적을 후하게 500 토큰으로 잡아도 ~135KB · 3ms.

### 결론

**새 의존성을 추가할 이유가 없다.** `lib/persist.ts`가 이미 필요한 걸 다 갖췄다 —
원자적 쓰기(temp+rename), 손상 파일 격리, 섹션별 파일 분리, 디바운스 비동기 저장.
SQLite(better-sqlite3)는 네이티브 의존성 + 두 번째 저장 패러다임을 들여오면서
이 규모에서 얻는 게 없다.

**단, 한계선을 명시한다.** `persist`는 섹션을 통째로 다시 쓴다(이번 세션에 3MB
history 블롭이 202ms 정지를 만든 그 구조다). 지금 규모에선 3ms라 무해하지만,
**`tokenRoutes`가 2MB(≈7500 토큰)를 넘으면** 그때는 per-token 파일 분리나 SQLite로
옮긴다. 그 전에는 과투자다.

- 파일: `data/state/tokenRoutes.json`
- 손상 시: 기존 격리 로직이 `.corrupt-<ts>`로 치우고 자동 재구축 (캐시라 안전)

## 4. 스키마

```ts
type TokenRouteDb = { schema: 1; tokens: Record<string, TokenRoute> }; // key = BASE

type TokenRoute = {
  base: string;              // "EUL"
  cgId?: string;             // CoinGecko id — 갱신용
  name?: string;
  chains: RouteChain[];      // 검증 통과한 체인만
  cexListed?: string[];      // 상장 CEX (6h)
  cexAt?: number;
  updatedAt: number;
  /** CoinGecko가 모르는 티커 — 짧게만 기억해 레이트리밋 낭비를 막는다 */
  unknown?: { at: number };
};

type RouteChain = {
  chain: string;             // 우리 체인 키 (chains.ts)
  contract: string;
  decimals: number;
  symbolVerifiedAt: number;  // 온체인 symbol() 통과 시각 — 없으면 저장 안 됨
  pairAddress?: string;      // DexScreener 최상위 풀
  liquidityUsd?: number;     // 1h 캐시 (표시·1차 필터 전용)
  liquidityAt?: number;
  withdrawNet?: Record<string, string>; // venue → net_type (7d)
};
```

**핵심 불변식: `chains[]`에는 온체인 `symbol()` 검증을 통과한 항목만 들어간다.**
검증 실패·확인 불가는 저장하지 않는다.

## 5. 보안 — 이 작업에 검증을 반드시 함께 넣어야 하는 이유

점검 보고서(`REVIEW_2026-07-25.md`) 남은 항목 1번과 직접 맞물린다.

지금 `resolveWalletAsset`은 **지갑이 보유한 토큰 중 심볼·체인이 일치하는 첫 컨트랙트**를
그대로 실전송에 쓴다(`lib/tokens.ts` ②단계). 온체인 `symbol()` 검증은 cex-dex **탐지**
경로에만 있고 **실행 경로엔 없다.** 심볼이 겹치는 에어드랍 클론 토큰이 EVM 지갑에
흔한데, 그걸 거래소 입금주소로 보내면 진짜 코인은 지갑에 남고 매도 다리는 없는 물량을
팔려 한다.

**컨트랙트를 영속화하면 잘못된 항목도 영속화된다** — 위험이 커진다. 그래서:

1. DB에 넣기 전 **온체인 `symbol()` 검증 필수**, 불일치·확인불가는 저장 안 함
2. `resolveWalletAsset`의 우선순위를 **①DB(검증됨) → ②큐레이션 → ③토큰리스트 →
   ④지갑 보유분** 으로 바꾼다 (지갑 보유분을 최하위로)
3. 지갑 보유분만 근거일 때는 **전송 전 그 자리에서 검증**하고 실패 시 fail-closed
4. 저장된 검증도 30일 지나면 재검증 (컨트랙트 교체·프록시 업그레이드 대비)

즉 이 DB는 성능 작업이면서 **동시에 알려진 보안 구멍을 닫는 작업**이다.

## 6. 신규 상장이라는 함정 — 프리워밍이 짝이다

**상장따리에서 정작 중요한 코인은 정의상 DB에 없다.** 처음 보는 코인이니까.
DB만으로는 승부처가 안 빨라진다.

→ **감지 즉시 백그라운드 프리워밍.** `registerPlay`가 상장을 감지하는 순간
`void ensureRoute(base)`를 던진다. 사용자가 패널을 여는 건 보통 그로부터 수 초 뒤라,
그때는 이미 준비돼 있다. 알림·자동매수 경로는 **절대 기다리지 않는다**(지금 반응
370ms를 지켜야 한다 — 프리워밍은 fire-and-forget).

DB는 그 결과를 **재시작 후에도 유지**시키는 역할이다. 지금은 메모리 캐시라 재기동
한 번에 전부 날아간다.

## 7. 구현 계획

```
lib/tokenRoutes.ts   (신규)
  getRoute(base)            → TokenRoute | null   (동기, 메모리 + 디스크 하이드레이션)
  ensureRoute(base)         → Promise<TokenRoute | null>  (없거나 만료면 구축·검증·저장)
  refreshLiquidity(base)    → 배경 갱신 (1h)
  verifyChain(chain, addr, base) → 온체인 symbol() 대조
```

| 배선 지점 | 변경 |
|---|---|
| `lib/listingDetail.ts` | 컨트랙트·페어를 DB에서 읽고, **견적만** 라이브 |
| `lib/tokens.ts` | `resolveWalletAsset` 우선순위 재정렬 + 전송 전 검증 |
| `lib/listings.ts` | `registerPlay`에서 `void ensureRoute(base)` 프리워밍 |
| `lib/persist.ts` | 변경 없음 (`tokenRoutes` 섹션만 추가) |

### 기대 효과

| 시나리오 | 지금 | 예상 |
|---|---|---|
| 신규 상장, 감지 후 패널 열기 | 0.4~1.7초 | **~0.1초** (프리워밍 적중) |
| 재조회(같은 세션) | 0.006초 | 0.006초 (변화 없음) |
| 재시작 후 첫 조회 | 0.4~1.7초 | **~0.15초** (디스크에서 복원) |
| 실행 직전 재견적 | 라이브 | 라이브 (변화 없음) |

> 신규 상장 수치는 프리워밍이 사용자보다 먼저 끝난다는 전제의 **추정치**다.
> 감지→패널 열기 간격이 1초 미만이면 여전히 기다린다.

### 하지 않을 것

- 가격·견적·슬리피지 캐싱 (위 2절)
- SQLite 도입 (2MB 넘기 전까지 과투자)
- 전체 토큰 유니버스 사전 크롤링 — 우리가 볼 코인만 lazy + 프리워밍으로 충분하고,
  대량 크롤링은 CoinGecko 레이트리밋 예산을 상장 순간을 위해 남겨둬야 한다

## 8. 리스크

| 리스크 | 완화 |
|---|---|
| 낡은 컨트랙트로 전송 | 30일 재검증 + 전송 전 온체인 검증 + fail-closed |
| DB 손상 | 캐시라 재구축 가능 · persist가 자동 격리 |
| 프리워밍이 감지 반응을 늦춤 | fire-and-forget, 알림·자동매수 경로에서 절대 await 안 함 |
| 파일 비대화 | 2MB 초과 시 per-token 파일 또는 SQLite로 전환 (임계 명시) |
| 검증이 RPC 장애로 실패 | 저장 안 함 → 다음 기회에 재시도 (fail-closed, 조용히 통과 금지) |
