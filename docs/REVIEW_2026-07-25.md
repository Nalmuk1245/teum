## P0 — 지금 실제로 고장나 있는 것

### 1. 스캔 캐시가 영구히 얼어붙는다 (지금 이 순간 그 상태) — **[실측]**

점검 중 실행 중인 서버가 이 상태였습니다:

```
refreshing: true      ← 갱신이 "진행 중"으로 걸려 있음
tsAgeSec:   12900     ← 마지막 스냅샷 3.6시간 전, 계속 증가
loopArmed:  true      ← 3초 루프는 살아서 돌고 있음
oppCount:   69        ← 낡은 데이터를 계속 서빙
```

**메커니즘** (`lib/scanCache.ts:52-66`, `:112-119`):
`refresh()`는 `C.refreshing = true`로 잠그고 `await scanAll()` 후 `finally`에서 풉니다.
`scanAll()`이 **끝나지 않으면** `finally`가 영원히 실행되지 않고, 이후 모든 3초 틱은
`if (C.refreshing) return`으로 즉시 빠지며, stale-while-revalidate 경로(`:117`)도
`!C.refreshing` 조건 때문에 함께 죽습니다. → **재시작 전까지 영구 동결.**

**왜 안 끝났나**: 스캔 경로의 티커 fetch에 타임아웃이 전혀 없습니다 — `lib/exchanges.ts:35,37`
(Binance bookTicker/24hr), `:94,104,128` (Upbit), `:174,191` (Bithumb), `:349,354` (FX).
나중에 추가된 bybit(`:239`)·okx(`:289`)는 `AbortSignal.timeout(6000)`이 있어, 누락은 의도가
아니라 빠진 것으로 보입니다. `lib/transfers.ts:28,71,99`도 동일 (`:99`는 가장 무거운 서명 엔드포인트).

**왜 심각한가 — 조용히 실패합니다:**
- 보드는 **살아 보입니다.** WS(`useLivePrices`)가 계속 가격을 갱신하므로 숫자가 움직입니다.
- 그런데 라이브 진입은 전부 막힙니다: `lib/execStep.ts:123`이 2분 넘은 스냅샷을 거부
  (`"기회 스냅샷 2분 초과"`). 즉 **모든 실행이 차단된 채 UI만 정상으로 보입니다.**
- **pm2로 잡히지 않습니다.** 프로세스가 죽지 않고 살아서 멈추므로, RUNBOOK의 pm2 자동
  재시작(112-119행)은 이 고장에 무효입니다.
- 워치독은 3분이면 감지하지만(`lib/watchdog.ts:33`) `telegramConfigured()`가 false면
  **아무 말도 하지 않고**(`:30`), 감지해도 **복구는 하지 않습니다.**
- `/api/health`가 503을 반환하지만 이를 폴링하는 주체가 없습니다.

**수정**
1. 스캔 경로 모든 fetch에 `AbortSignal.timeout(2500)`.
2. `refresh()`를 하드 데드라인으로 감싸기 — `Promise.race([scanAll(), deadline])`. 한 틱은
   부분 데이터로라도 **항상 끝나야** 합니다.
3. 스턱 복구: `refreshStartedAt`을 기록하고 30초 초과 시 `refreshing`을 강제 해제.
   (1번만 해도 이번 원인은 막히지만, 3번이 없으면 앞으로 안 끝나는 다른 promise가 생길 때
   같은 영구 동결이 재발합니다. 구조적 수정은 3번입니다.)
4. 워치독이 텔레그램 없이도 최소한 자기 복구(강제 해제 + 로그)는 하도록.

## P0 — 돈 경로

### 2. 재시도에 멱등성이 없다 → 출금·온체인 전송·스왑 이중 실행 — **[확인]**

멱등 캐시(`lib/execStep.ts:27-41`)는 **`app/api/exec-step/route.ts`에서만** 참조됩니다.
UI가 실제로 쓰는 경로는 `/api/runs` → `runEngine.loop` → `callStep`(`lib/runEngine.ts:150`)이고,
여기서는 `runStep`을 직접 호출해 **재실행 보호가 전혀 없습니다.** (즉 멱등 캐시는 사실상 死코드.)

실패 시 `eng.i`는 전진하지 않고(`:257` vs `:269`), `retryRun`은 같은 인덱스로 재진입합니다.
UI의 주 버튼이 "실패 지점부터 재시도"(`ExecuteModal.tsx:328`)입니다.

비가역 단계는 모두 **"실패했지만 실제로는 성공했을 수 있는"** 모드가 있습니다:
- `sendEvm`은 브로드캐스트 후 `tx.wait(confirms)`를 기다립니다(`lib/wallet.ts:94,100`).
  컨펌은 Polygon 100, ARB/OP 120회(`config.ts:108,114-115`) → RPC 타임아웃이면 `ok:false, hash:null`.
  재시도하면 **두 번째 온체인 전송.**
- 거래소 출금도 수락 후 네트워크 오류면 `catch`(`orders.ts:299-301`) → 재시도하면 **이중 출금.**

**수정**: `callStep` 안에서 멱등 키(`runId:stepIndex`)를 조회·기록. 그리고 `withdraw`/`transfer`/
`swap` 재실행 전에는 **상태를 먼저 조회**(출금 이력, tx receipt, 목적지 잔고)하고,
"불명"이면 자동 재시도 금지 — 수동 전용으로.

### 3. 정상적인 "입금 대기"가 서킷 브레이커를 트립시켜 런을 영구 고착시킨다 — **[확인]**

- 입금이 아직 안 들어오면 `checkDeposit`은 `ok:false` + `"입금 대기"`를 반환합니다
  (`orders.ts:461,478,495` 등). 대기용 상태가 아니라 **실패**입니다.
- 루프에는 폴링/대기 단계가 없어 이를 단계 실패로 처리하고(`runEngine.ts:235`),
  `i > withdrawIdx`라 `phase:"error"`, 그리고 **`recordExecFailure`를 호출합니다**(`:256`).
- `recordExecFailure`는 10분 내 3회면 **킬 스위치를 자동 ON**하고 모든 엔진에
  `cancelled = true`를 세팅합니다(`:80-89`).

전송은 원래 수 분 걸리고 사용자에게 주어진 수단은 재시도 버튼뿐이므로, **정상적인 김프 흐름이
재시도 3번 → 킬 스위치 자동 ON**으로 이어집니다. 주석(`:76-77`)은 "재검증 실패 같은 정상 방어는
세지 않는다"고 하지만, 코드는 슬리피지 상한·리스크 한도·스냅샷 만료 같은 **방어적 중단까지 모두
집계**합니다.

여기에 두 번째 결함이 겹칩니다: **`cancelled`는 어디서도 false로 되돌아가지 않습니다**
(`:86, :328, :364`에서 true만; 초기화는 신규 엔진 생성 시 `:303`). 그리고 가드가
`if (isKilled() && !eng.cancelled)`(`:195`)라서, 브레이커가 둘 다 세팅한 경우 **에러 표시조차
스킵**됩니다. 결과: 런이 UI에서 영구히 `"running"`, 텔레그램 없음, `retryRun`은 `phase==="error"`가
아니라서 거부, 킬 해제 후에도 복구 불가, 게다가 `inFlightUsd()`가 계속 그 금액을 세서
**노출 한도를 영구히 잡아먹습니다.**

**수정**: `deposit`을 폴링 단계(`phase:"waiting"` + 타임아웃)로 바꾸고, `recordExecFailure`는
실제 주문/출금/전송 API 실패만 집계. 킬 해제 시 `cancelled` 리셋(또는 per-engine 불린 대신
kill epoch 비교). 킬로 중단된 런은 반드시 `error`로 패치 + 알림.

### 4. bybit/OKX 주문이 체결량을 반환하지 않는다 — 방금 배선한 cross-cex의 실질적 한계 — **[확인]**

`bybitOrder`(`orders.ts:573`), `okxOrder`(`:627`), `bithumbOrder`(`:413`)는 `filledQty`/
`quoteFilled`를 설정하지 않습니다. 따라서 `callStep`의 `if (typeof r.filledQty === "number")`
(`runEngine.ts:158`)가 발동하지 않고, `qty`는 **스캔 시점 가격 기준 명목 수량**으로 남습니다
(`execStep.ts:111`).

bybit/OKX에서 매수하는 cross-cex 런(제가 어제 배선한 경로)의 실제 결과:
- 헷지가 명목 수량으로 걸려 스캔↔체결 가격차만큼 잔여 방향 노출이 남습니다.
- 출금이 실제 잔고를 초과 요청할 수 있어 → 거부 → 강제 롤백 시장가 덤프.
- `settle`이 실체결 분기(`execStep.ts:394`, `buyQuote && sellQuote` 필요)를 못 타서
  **`recordPnl`이 호출되지 않고**(`:411`) → **일손실 한도가 이 거래소들에 대해 작동하지 않습니다**
  (`risk.ts:70-73`).

즉 어제 커밋한 cross-cex는 **감지·게이트·플랜은 맞지만, 라이브 체결 회계가 비어 있습니다.**
`DRY_RUN=false` 전에 반드시 메워야 하는 구멍입니다.

**수정**: 주문 생성 후 체결 조회를 붙이기(`upbitOrderDetail`이 이미 하는 방식). 그리고 라이브에서
매수가 체결량을 못 주면 명목으로 진행하지 말고 **하드 실패**.

### 5. cex-dex buyDex 플랜이 가드 4개를 동시에 무력화한다 — **[확인]**

`execPlan.ts:48-55`의 플랜은 `[approve, swap, hedge, transfer, deposit, sell, close, settle]` —
**`buy` 단계도, `withdraw` 단계도 없습니다.**

- `runEngine.ts:237` `withdrawIdx = findIndex(..."withdraw")` → **-1**. `i <= -1`은 항상 false라
  **롤백 분기가 절대 실행되지 않고**, 모든 실패가 `"출금 이후: 헷지 유지, 수동 처리 필요"`(`:254`)로
  잘못 표시됩니다. DEX 매수 직후 헷지 실패 = 무헷지 롱이 방치됩니다.
- `checkEntry`(1회 규모 + 일손실), 2분 스냅샷 신선도, 최소 출금 사전 게이트, per-step `isKilled()`가
  전부 `buy` 케이스 안에만 있어(`execStep.ts:117-147`) **하나도 적용되지 않습니다.**
- `needsConfirmBefore`는 `beforeWithdraw`에서 `id === "withdraw"`에만 멈춥니다(`execPlan.ts:97`).
  UI에서 "권장"으로 표시되는 그 레벨인데, 이 플랜엔 withdraw가 없어 **비가역 `transfer`가 무확인 실행**됩니다.
- `eng.startTs`는 `buy` 단계에서만 세팅되므로(`runEngine.ts:144-148`) 0으로 남고, `deposit`이
  `Date.now() - 1h`로 폴백해(`execStep.ts:347`) **최근 1시간 내 아무 입금이나** 조건을 만족시켜
  실제 코인이 아직 이동 중인데 `sell`로 전진할 수 있습니다.

**수정**: 경계를 `findIndex("withdraw")`가 아니라 단계별 `irreversible: true` 플래그에서 유도.
`checkEntry`/킬/신선도를 `callStep`의 단계 무관 프리플라이트로 승격. `startTs`는 모든 플랜의 첫 단계에서 세팅.

### 6. 롤백 후 재시도가 완료 상태를 확인하지 않아 재실행된다 — **[확인]**

롤백 루프(`runEngine.ts:241-251`)는 `step.id`만 보고 분기하며 **`statuses[sid]`를 확인하지 않습니다.**
그리고 롤백이 끝난 뒤에도 `eng.i`는 실패 인덱스에 남고 재시도 버튼이 주 액션입니다.

시나리오(김프, 헷지 ON): 매수 체결 → `hedge` 실패(증거금 게이트 `execStep.ts:205`) → 롤백이 현물을
시장가 매도 → 사용자가 재시도 → `hedge`가 실제로 실행 → **현물 없는 네이키드 숏.** 이후 `withdraw`가
잔고 없음으로 실패하고, 롤백 루프가 `buy`를 다시 시장가 **매도**합니다(다른 재고가 있으면 의도치 않은 매도).

**수정**: 롤백 루프는 `statuses[sid] === "done"`인 단계만 되돌리기. 롤백이 한 번 실행된 런은
**종결 상태**로 만들고 재시도 대신 신규 런을 요구.

### 7. 청산(unwind)이 실행 루프와 동시에 돌 수 있다 → 이중 매도 — **[확인]**

`unwindRun`(`runEngine.ts:345-360`)은 `run.unwinding`과 `remaining > 0`만 보고 **`eng.busy`나
`phase`를 확인하지 않습니다.** UI는 `statuses.buy === "done" && remaining > 0`이면 청산 버튼을
노출합니다(`ExecuteModal.tsx:369-371`) — 즉 루프가 `withdraw`/`deposit`/`sell` 중일 때도 눌립니다.

또한 `unwindRun`은 ~40초 `await` 전에 `run`을 캡처한 뒤 `remaining`을 덮어씁니다(`:351-355`).
그 사이 루프의 `sell`이 `remaining = 0`으로 만들었다면(`:267`) **없는 포지션이 UI에 되살아나고**,
다음 청산 클릭이 실제 재고를 팝니다.

DRY_RUN에서는 `unwind()`가 완전 시뮬로 빠지므로(`lib/unwind.ts:44-75`) **이 상호작용 전체가
한 번도 실행되지 않은 코드**입니다.

**수정**: 런당 뮤텍스 — `eng.busy`/`phase === "running"`이면 청산 거부. `await` 후에는 캡처본이 아니라
`E.runs[id]`를 다시 읽기.

## P1 — 속도

### 8. persist가 3.12MB를 동기로 통째 재직렬화 → 202ms 이벤트루프 정지 — **[실측]**

실제 `data/state.json`으로 측정: **`JSON.stringify` 154ms + `writeFileSync` 48ms = 약 202ms**의
완전 동기 블록 (`lib/persist.ts:42,55`). 그 시간 동안 fetch도, `/api/scan` 응답도, 상장 공지
폴링도 전부 멈춥니다.

파일의 **97%가 gap history**입니다 — `history` 3.53MB / 전체 3.12MB, 105 트랙.
`lib/history.ts:84`가 매 스캔(3초) `saveSection("history", ...)`을 호출하고 디바운스가 30초로
묶으므로 → **30초마다 202ms 정지 + 하루 약 9GB 디스크 쓰기.**

더 나쁜 것: `runEngine.ts:92-101`의 `persistRuns`는 **500ms** 디바운스이고 `patch()`가 모든 단계
전이에서 호출됩니다 → **돈이 이동하는 중에 500ms마다 202ms씩 멈춥니다.** 그리고 `runs` 섹션은
수 KB인데도 매번 3MB history를 함께 재직렬화합니다.

KR 박스에서는 종목이 늘어 history가 ~14MB로 커지면 정지가 **~1초**로 갑니다.

**수정**: (a) 섹션별 파일 분리 — `flushSection("runs")`가 KB만 쓰게. (b) 디바운스 경로는
`fs.promises.writeFile`. (c) 샘플을 `[ts,gross,price]` 배열로 패킹하거나 다운샘플 —
30분치 3초 해상도 원본이 재시작을 넘어 살아남을 필요는 없습니다.

### 9. 스캔 틱이 3초 케이던스를 거의 포화시킨다 — **[실측]**

측정된 틱 임계경로: **Upbit ~1.8초**, Bithumb ~1.0초, Binance ~380ms(60초마다 ~1.17초),
bybit/okx 각 ~170ms. 실제 틱 비용 **~1.8~2.0초**, TTL 만료 틱에서 **2.5~3초+**.
`lib/scanner.ts:32`의 주석("~1.2s")은 낡았습니다.

회수 가능한 것들:
- **Upbit `market/all`을 매 틱 재조회**(1.0초, 61KB) — 게다가 `lib/listings.ts:274`의
  `pollMarkets`가 **같은 URL을 같은 3초 주기로** 또 부릅니다. TTL 캐시로 묶으면 됩니다.
- **Upbit 티커 청크가 직렬** — `exchanges.ts:102-121`이 `for` 안에서 `await fetch`
  (3청크 ≈ 550ms 직렬). 바로 아래 오더북 청크(`:127`)는 이미 `Promise.all`이라 단순 누락입니다.
  Upbit 제한은 10 req/s라 3병렬은 여유.
- **Bithumb 2콜 직렬**(`:174` 564ms → `:191` 416ms, 데이터 의존 없음) → `Promise.all`로 ~420ms 회수.
- **Binance 24hr 1.83MB** → `JSON.parse`만 251ms 동기 블록, 3662행 중 713행만 사용(`:43`).

### 10. 상장 알림 경로에 피할 수 있는 순차 왕복이 있다 (모트 지연) — **[확인]**
